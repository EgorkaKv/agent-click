# Эксперимент: Haiku 5.5 как субагенты для написания кода

**Вопрос.** Насколько хорошо Haiku 5.5 пишет модули по чёткому ТЗ, если архитектуру, структуру и контракт задаёт основная сессия (Opus 5.5)?

**Постановка (2026-10-26).**
- Основная сессия сделала каркас: `package.json`, конфиги, сборку скрипта страницы, контракт `src/types.ts`, тестовый стенд (`test/helpers/browser.ts`, headless Brave с временным профилем).
- Три агента Haiku 5.5 параллельно, каждый в своей папке, ТЗ в этой директории:
  - A — [task-a-page.md](task-a-page.md): скрипт в странице (сбор элементов, номера, locate). Самый сложный.
  - B — [task-b-render.md](task-b-render.md): текст `look`, дифф, метки на скриншоте. Чистые функции.
  - C — [task-c-browser.md](task-c-browser.md): подключение, сеть, стабилизация, CDP-ввод.
- Агентам запрещено менять контракт и чужие модули; проблемы контракта — в отчёт.

**Критерии оценки (заданы до получения результатов).**
1. Тесты агента проходят; typecheck его папки чистый.
2. Соответствие ТЗ: пункт за пунктом, что сделано, что пропущено молча (хуже, чем пропущено с объяснением).
3. Качество тестов: проверяют ли поведение или подогнаны под реализацию.
4. Честность отчёта: совпадает ли отчёт с тем, что в коде.
5. Объём правок основной сессии при интеграции.
6. Время и токены.

Исходный вывод агентов сохраняется до правок, чтобы правки можно было измерить.

### По критериям

1. **Тесты и typecheck.** Свои тесты у всех зелёные. В общем прогоне 17 файлов параллельно запускали 17 headless Brave, и тайминговые тесты падали от перегрузки. Это недочёт стенда основной сессии: исправлено `maxWorkers: 4`. Плюс одна хрупкая граница в тесте C (`>= 650` при опросе раз в 50 мс; ослаблено до 600). После этого 157/157 стабильно.
2. **Соответствие ТЗ.** B — полное, оба примера формата воспроизводятся байт в байт. C — полное. A — по отчёту всё; реестр номеров (самое важное) сделан точно по D-9 е. Проверка на живом сайте — ниже.
3. **Качество тестов.** Тесты проверяют поведение, а не реализацию: C поднимает локальный HTTP-сервер с 200/409 и проверяет тело ошибки, `isTrusted` у клика, кириллицу в `insertText`; A проверяет переживание `replaceWith` и непереиспользование номеров.
4. **Честность отчётов.** Все трое сами перечислили упрощения и отклонения от ТЗ (B — лимит в `formatDiff`, C — добавленный `drain()`, A — 9 упрощений, включая пограничную производительность 46–48 мс). Одна неточность: C заявил, что Chromium не завершает fetch, пока страница не прочитала тело ответа; проверка показала, что для небольших ответов это неверно (обобщение из частного случая).
5. **Правки основной сессии.** В коде модулей — 0 исправлений багов. Интеграция: вызов `drain()` из `act` (по отчёту C). Инфраструктура тестов — 2 строки.
6. **Время и токены.** Сумма ~463 тыс. токенов Haiku, параллельно ~17 мин по стене (по самому долгому агенту).

### Замечания к коду (недочёты ТЗ, а не агентов)

- B: кавычки внутри имён и значений не экранируются; метка не накрывает свой элемент, но может лечь на соседний.
- A: роли `clickable` и `generic` не описаны в контракте; `snapshot({scope})` бросает исключение при ненайденной области; `describe` возвращает null для неоднозначного мёртвого номера.
- C: `NetworkRecorder` игнорирует тип `Other` целиком (по формулировке ТЗ «Ping/Other beacons»).

### Живой прогон (2026-10-26, RevenueCat в Brave пользователя)

`scripts/try-look.ts`: подключение 12 с (ожидание Allow), `look` 288 мс, 1,5 тыс. символов текста, скриншот 75 КБ. Дерево контекста (`header`, `nav`, `main › section "Reporting"`), значения, состояния и `disabled` — корректны.

Найденные проблемы:
1. **(A) Обрезка скролл-контейнером.** Пункты внутри прокручиваемого `nav` и поле над видимой частью прокручиваемого `main` помечены `occluded by nav`, хотя они просто прокручены за край контейнера. Должны считаться «за экраном». Агент A сам указал это в отчёте как неучтённое.
2. **(A) Контейнер с `tabindex`.** Прокручиваемая область `main` с `tabindex=0` попала в список как `[27] generic "AppsFlyer Integration | General Configurationinfo…"` — длинное имя из всего текста и огромная рамка на скриншоте. Нужно отсекать элементы, попавшие только по `tabindex`, если внутри есть другие интерактивные.
3. **(B, ошибка ТЗ) Метки в плотных списках.** Порядок позиций «снаружи сверху-слева» в первую очередь привёл к тому, что метка элемента лежит на нижнем краю предыдущего пункта списка — читается как метка соседа. Это ошибка ТЗ основной сессии, а не агента: лучше метка внутри левого верхнего угла, если элемент достаточно высокий.

**Вывод по эксперименту.** Haiku 5.5 при подробном ТЗ, готовом контракте и тестовом стенде пишет рабочие модули без багов, которые пришлось бы чинить, честно отчитывается и быстро исправляет конкретную обратную связь. ### Живой прогон 2 (Gemini в Brave пользователя)

Подключение 3,4 с, `look` 359 мс. Проблемы раунда 1 исправлены: скрытые прокруткой пункты больше не «перекрыты», контейнер с `tabindex` не попадает в список, метки стоят внутри своих элементов.

Новые проблемы:
1. **Ложный `⏳ loading`** (`loading in page, loader in main`): регулярка по классам `loading|loader` слишком широкая — ловит постоянные элементы. Нужно требовать видимый небольшой элемент (спиннер) или `aria-busy`, а не любое совпадение класса.
2. **Шум в `Messages`**: `aria-live`-область чата целиком (весь ответ модели) попала в сообщения. Длинные live-области и области с интерактивными элементами — не сообщения.
3. **Слабое описание перекрытия**: `occluded by main` — на деле кнопки перекрыты плавающей панелью ввода. `describeOccluder` должен описывать ближайший fixed/sticky элемент под точкой, а не landmark.
4. **Метка внутри элемента закрывает первые буквы текста** («локноты», «рифт контекста…»). Компромисс: номер всегда однозначно у своего элемента, текст элемента агент получает в списке. Пока оставляем.

### Раунд 4: новый агент E по первой реальной сессии ([task-e-page-fixes.md](task-e-page-fixes.md))

Свежий агент Haiku, короткое ТЗ на четыре правки в `src/page/` (scope по landmark, имена безымянных контролов, числовые заголовки, дубль статуса в Messages).
