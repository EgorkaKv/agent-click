# Self-report: Flowr — подготовка релиза в App Store Connect и Google Play

Сессия: агент заполнял App Store Connect (ASC) и Google Play Console через Claude in Chrome. Работа: тексты карточек на 3 языках, загрузка 24+ скриншотов, мастера App Privacy и возрастного рейтинга, данные для ревью, разбор черновиков заявок.

**Честная оговорка про контекст.** Сессия была сжата (compact) посередине. Первую половину я знаю только по своему конспекту, без деталей шагов. Она включала:
- Play Console: декларации, кнопку Save;
- мастер App Privacy в ASC;
- первую загрузку скриншотов PL и UK;
- возрастной рейтинг.

Эпизоды из неё помечены **[по конспекту]**. Всё остальное я помню напрямую.

---

## 1. Восприятие

**Скриншот почти бесполезен на тяжёлом SPA.**
- Окно было 1280×543, на экран влезало 2–3 поля формы.
- Первый скриншот страницы «Информация о приложении» показал пустую белую область: SPA ещё грузилась. Отличить «загружается» от «пусто» по картинке нельзя.
- На ASC скриншоты часто падали по таймауту **[по конспекту]**.
- В итоге почти всё чтение шло через `javascript_tool` → `document.querySelector('main').innerText.slice(i, i+N)` с поиском по якорному тексту («Сборка», «(средний дисплей)»).

**`get_page_text` возвращал только навигацию**, без основного контента **[по конспекту]**. Отсюда привычка читать `main.innerText` кусками по ~700–1500 символов.

**`find` (поиск на естественном языке) ненадёжен в обе стороны.**
- На запрос «file input для скриншотов» он ответил, что такого нет. Input существовал, но лежал в неактивной вкладке «Видео и снимки экрана». Пришлось сначала кликнуть вкладку.
- В боковой панели «Черновики» он сказал, что регион свёрнут и кнопок «Удалить» не видно, хотя панель была открыта. Пришлось перейти на координаты и `zoom`.
- Он возвращает ref без гарантии, что элемент жив. Я получил тот же `ref_463` до и после «Удалить все» и не знал, можно ли ему доверять.

**Поля формы без понятных подписей.** В блоке «Информация для проверки» у шести input общие подписи: «Информация для входа» ×2 и «Контактная информация» ×4. Сопоставить поле и смысл удалось только по `id` (`demoAccountName`, `contactPhone`…) и `placeholder`. Ни один инструмент не отдаёт «поле → его подпись → значение» одним списком.

**К чему относится элемент.**
- Трудно понять, в каком диалоге или панели находится кнопка. Самая неочевидная деталь: какая из трёх карточек черновика открыта.
- В одном черновике вместо названия подписки висел спиннер, и что это Weekly, я узнал только из `innerText` всей панели.
- Текущую локаль формы (польский или en-US) тоже определял через JS-поиск кнопки с названием языка.

**UI расходился с реальным состоянием.** Это самый важный пункт.
- ASC показывал «Снимки экрана приложения (8 из 10)», то есть всё якобы загружено. На деле все уменьшенные скриншоты PL, UK и EN были в состоянии `FAILED` на сервере: у файлов была полупрозрачная альфа по краям.
- Узнал я это только GET-запросом к внутреннему API (`/iris/v1/appScreenshotSets?include=appScreenshots`, поле `assetDeliveryState`).
- Скриншоты PL и UK пролежали сломанными со времени прошлой загрузки, и я считал их готовыми.
- Аналогично: API отдавал подпискам `MISSING_METADATA`, а UI писал «Готово к просмотру». Настоящая причина (подписки застряли в отдельных черновиках) была видна только в UI-панели.
- Вывод: ни скриншот, ни дерево доступности не отражают асинхронное серверное состояние.

**Фильтр вывода JS мешал читать.** Скрипт, который перечислял input'ы со значениями, вернул `[BLOCKED: Cookie/query string data]`: видимо, значения выглядели как URL. Пришлось переписывать запрос, чтобы он не возвращал значения.

## 2. Действия

**Выпадающее меню языка.**
- Клик по `ref` из `find` по кнопке «польский» ничего не открыл: меню не появилось ни в DOM-проверке, ни на скриншоте. Клик по координатам открыл.
- Пункт «английский (США)» выбирал тоже по координатам, со скриншота.
- Позже переключал языки целиком в JS: клик по кнопке, затем поиск листового узла с точным текстом «украинский» и `.click()`. Так быстрее и надёжнее, но это обход инструмента.

**React-поля.**
- `form_input` я не использовал вообще. Заполнение шло через нативный setter `HTMLInputElement.prototype.value` / `HTMLTextAreaElement.prototype.value` плюс события `input`, `change` и `blur`. Иначе React не видит изменения, и кнопка «Сохранить» не активируется.
- Описание на 1300 символов с переносами и типографскими кавычками вставлял строковым литералом в JS. Это хрупко из-за экранирования.

**Загрузка файлов.** Самое трудоёмкое место сессии.
1. `file_upload` принимает только файлы, доступные сессии. Пришлось копировать скриншоты в scratchpad **[по конспекту]**.
2. Лимит 10 МБ на один вызов. 8 файлов по 1–2,7 МБ приходилось резать на 2–3 партии вручную, считая размеры.
3. После каждой загрузки ASC перерисовывает input, и старый ref указывает на отсоединённый элемент. Загрузка в него «успешна», но ни к чему не приводит. Отсюда цикл «загрузить → подождать 8–10 с → `find` заново → загрузить следующую партию».
4. Из-за этого в прошлой половине часть файлов молча потерялась, а другие встали не в том порядке, и PL5/PL6 пришлось перезаливать **[по конспекту]**.
5. Ответ `file_upload` («Uploaded 3 files») ничего не говорит о том, принял ли их сайт.

**Модальные подтверждения.** «Удалить все» → модалка «Удалить» и «удалить его» → модалка «Удалить из отправки?». Каждая занимает отдельный `find` или скриншот, чтобы найти кнопку подтверждения и убедиться, что модалка про нужный объект: в ней был текст «(язык: польский)».

**Почему уходил в JS или координаты вместо ref.**
- ref не находился (неактивная вкладка, панель);
- клик по ref не срабатывал (меню языка);
- нужно было атомарно сделать «открыть меню → выбрать пункт → дождаться перерисовки → прочитать результат», а через отдельные вызовы это 4–5 шагов;
- нужно было прочитать данные, которых в DOM нет (серверный статус).

**Блокировки.** Классификатор запретил DELETE-запрос через `fetch` к внутреннему API («External System Writes»). Это разумно, и я сделал то же через UI. Но получилось три удаления × (кнопка → модалка → подтверждение → проверка) вместо одного вызова. Кнопку Save в Play Console тоже заблокировали, её нажал владелец **[по конспекту]**.

**Сбои вкладки.**
- Один раз все инструменты, включая скриншот, начали возвращать `Cannot access a chrome-extension:// URL of different extension`. Скорее всего, в вкладку внедрилось другое расширение (менеджер паролей) после ввода логина. Помог только повторный `navigate`.
- Через пару дней вкладка оказалась «не в группе этой сессии», и пришлось создавать новую.

## 3. Проверка результата

**Надёжнее всего — сеть, а не экран.** После «Сохранить» я читал `read_network_requests` с фильтром `iris/v1` и смотрел методы и статусы: `POST appInfoLocalizations 201`, `PATCH appStoreVersionLocalizations 200`, `POST appStoreReviewDetails 201`.
- По конспекту, одно сохранение молча вернуло 409, потому что название «Flowr» уже занято в en-US. На экране это было не видно.
- Перед действием приходилось делать `read_network_requests(clear: true)`, иначе в ответе оказывалось 957 старых запросов.

**Вторая линия — перезагрузить страницу и прочитать поля.**
- Так обнаружилось, что заметки для ревью из прошлой половины сессии **не сохранились**: поле было пустым, хотя в конспекте я записал их как сделанные. Только теперь пришёл `POST appStoreReviewDetails 201`, то есть записи раньше не существовало.
- Перезагрузка с ожиданием появления полей (цикл до 20 с) — это 2 вызова на каждую проверку.

**Асинхронная обработка.** Для скриншотов я писал в странице хелпер `window.__ss(locId)`, который делал GET по API и печатал `fileName/state`, и вызывал его с `sleep` 15–30 с, пока не становилось `COMPLETE`. Без этого я бы сдал заявку, которую ASC не пропустил бы.

**Повторные скриншоты только ради проверки.** После compact примерно 12–15: открылось ли меню, открылась ли модалка, что в черновике, ушёл ли спиннер «Обработка». Ещё 3 `zoom` по панели черновиков, потому что мелкий текст на полном скриншоте не читается.

## 4. Скорость: где терял больше всего

1. **Скриншоты, всего ~45 вызовов после compact.** Это 3 локали × (удалить все → подтвердить → найти input → загрузить партию 1 → ждать → найти input → загрузить партию 2 → проверить статус через API) плюс диагностика `FAILED`: разбор PNG-заголовков, альфа-канала, пересборка через PIL. Половина шагов — механика (повторный поиск input, ожидание), которую инструмент мог бы делать сам.
2. **Переключение локали и навигация**, ~10 вызовов: открыть меню, выбрать, подождать, проверить, что форма теперь именно en-US, а не всё ещё PL с подставленными значениями. После переключения форма en-US была предзаполнена польскими значениями, и это сбивало.
3. **Расследование «где подписки»**, ~20 вызовов: несколько запросов к API, в которых я ошибался в именах `include` и получал `undefined`; навигация по трём черновикам; три удаления через UI.
4. **Ожидания вслепую.** Фиксированные `wait 3–10 с` и `setTimeout` внутри JS вместо «дождаться, когда X».
5. **Харнесс постоянно напоминал «используй browser_batch».** Батчить было почти нечего: каждый следующий шаг зависел от результата предыдущего (новый ref, появилась ли модалка).

## 5. Идеальный инструмент

Принцип: **каждое действие само дожидается стабилизации и возвращает дифф**: что изменилось на странице, какие появились диалоги и ошибки, какие изменяющие запросы ушли и с каким статусом. Тогда отдельный скриншот «для проверки» почти не нужен.

### Вызовы

1. **`observe(scope?)`** — структурный снимок того, что видит пользователь:
   - дерево областей (`main`, `dialog`, `drawer`, `menu`, `tabpanel(active/inactive)`) со стабильными id, которые переживают перерисовку и привязаны к семантике, а не к DOM-узлу;
   - для полей: `label` (найденная подпись, включая `aria`, `placeholder` и ближайший заголовок группы), `value`, `disabled`, `invalid`, текст ошибки;
   - кнопки с `enabled`;
   - баннеры, тосты, ошибки валидации отдельным списком;
   - индикаторы загрузки (`busy: true`, если есть спиннер или скелетон);
   - параметр `scope: "dialog:top"` или текст-якорь, чтобы не тащить всю страницу.
2. **`act(target, action, value?)`**:
   - `target` — семантический: `{role:"button", name:"Сохранить", within:"Информация о приложении"}` или id из `observe`;
   - действия: `click`, `fill` (сразу правильный путь для React), `choose`, `check`, `submit`;
   - после действия ждёт `network idle + DOM stable` и возвращает `{changed: [...], opened: dialog|menu|null, errors: [...], requests: [{method, path, status}]}`.
3. **`fill_form({ "Название": "...", "Подзаголовок": "..." }, within?)`** — сопоставление по подписям, многострочный текст без экранирования, ответ по каждому полю: `found / set / rejected (maxlength 30)`.
4. **`choose(trigger, option)`** — открыть дропдаун, меню или combobox и выбрать пункт по тексту за один вызов. Возвращает новое значение триггера. Это покрыло бы все переключения языка.
5. **`upload(target, files, {order: true})`**:
   - сам режет на партии под лимит;
   - перед каждой партией заново находит input;
   - ждёт, пока сайт покажет каждый файл;
   - возвращает список `{file, accepted, position, siteError}`.
6. **`wait_for(condition, timeout)`** — условие: текст появился или исчез, элемент стал `enabled`, запрос по шаблону завершился, `busy=false`, JS-предикат стал true. Вместо `sleep`.
7. **`network(since: "last_action", mutating_only: true)`** — по умолчанию только POST/PATCH/PUT/DELETE с кратким телом ошибки. Например, для 409: `{"code":"ENTITY_ERROR.ATTRIBUTE.INVALID", "detail":"name already used"}`.
8. **`read_api(url)`** — явно read-only GET с сессией страницы, ответ в JSON. Отделён от записи, чтобы политика безопасности могла разрешать его без вопросов, а запись — нет. В этой сессии read-only GET к `/iris/v1/...` был единственным источником правды о `FAILED` и `MISSING_METADATA`.
9. **`confirm(dialog_match, button)`** — подтвердить модалку, только если её текст совпадает с ожидаемым (`"язык: польский"`). Защищает от подтверждения не того объекта.
10. **Самовосстановление вкладки.** Устойчивый handle вкладки между днями; при «чужом расширении» или потере группы — автоматический reload и повтор, с пометкой в ответе.

### Как выглядели бы трудные моменты

**A. Английская локализация: имя, тексты, сохранение.**
Сейчас: ~15 вызовов (меню по координатам, скриншоты, JS-сеттеры, network clear/read, перезагрузка для проверки).

```
choose({name:"польский", within:"Локализуемая информация"}, "английский (США)")
→ {value:"английский (США)", form_reset:true, prefilled_from:"pl"}

fill_form({"Название":"Flowr: Plant Care", "Подзаголовок":"AI plant diagnosis & reminders"})
→ [{field:"Название", set:true}, {field:"Подзаголовок", set:true, length:30, max:30}]

act({role:"button", name:"Сохранить"}, "click")
→ {requests:[{POST /appInfoLocalizations 201}], errors:[], changed:["Сохранить: disabled"]}
```

Три вызова, и сохранение подтверждено в ответе. Если бы имя было занято, `errors` сразу показал бы 409 с причиной, а не тишину, как было **[по конспекту]**.

**B. Скриншоты для трёх локалей.**
Сейчас: ~45 вызовов и ни одного сигнала об ошибке от инструментов.

```
upload({slot:"iPhone с Dynamic Island", locale:"en-US"}, ["EN1.png",…,"EN8.png"], {order:true, wait_processing:true})
→ [{file:"EN1.png", accepted:true, position:1, server_state:"FAILED", reason:"ASSET_FAILED"}, …]
```

Если инструмент не умеет ждать серверную обработку, то хотя бы `warnings:[...]` с ошибками, которые сайт показывает у миниатюр. Показывал ли ASC такие ошибки, не знаю: миниатюры я ни разу не рассматривал, потому что верил счётчику «8 из 10». Ошибку `FAILED` я бы увидел в первом же ответе, а не после расследования.

**C. «Где выбрать подписки».**
Сейчас: ~20 вызовов, из них несколько неудачных запросов к API.

```
observe({scope:"drawer:Черновики", expand:true})
→ drafts:[
    {id:"d1", created:"26 июля 12:57", items:[{name:"Flowr Annual", type:"Подписка"}], submit_enabled:false},
    {id:"d2", created:"12:53", items:[{name:"Flowr Monthly"}]},
    {id:"d3", created:"12:48", items:[{name:"Flowr Weekly"}],
     errors:["подписка должна быть отправлена с группой", "добавьте версию приложения"]}]
```

Один вызов показал бы полную картину и причину: подписки застряли в трёх черновиках без версии. Не нужно было бы открывать каждый черновик, делать `zoom` по спиннеру и сверять с API.
