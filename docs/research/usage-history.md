На решение «TS, а не Rust» это не влияет: задержки внутри инструмента объясняются фиксированными паузами и ожиданиями (см. claude-in-chrome.md), а не скоростью языка. ## Качественный разбор

### 3bbafecf: Play Console и App Store Connect, анкеты и метаданные flowr

**Задача.** Метаданные версии на трёх языках, по 8 скриншотов на язык, App Info, цена и доступность, анкета App Privacy (10 типов данных, по 7 шагов мастера на каждый), возрастной рейтинг, отправка на ревью. Интерфейсы — тяжёлые SPA: Angular Material и React, с модальными мастерами и dropzone со скрытым `<input type=file>`.

**Как работал агент.** Типичный цикл: `find` → `browser_batch[click ref, wait N, javascript_tool(прочитать innerText)]`. `find` вызывался почти перед каждым кликом, потому что без полного `read_page` ref неизвестны. Состояние агент читал в основном через JS-срезы `innerText`, скриншоты и `read_page` почти не использовал. После compact перешёл на цикл «скриншот → клик по координатам → скриншот» без батчей.

**Трения:**
- **Фиксированные ожидания.** 126 действий `wait` (~610 с) и ~214 с `setTimeout` внутри JS — около 35% всего времени инструментов. `find` на недогруженной странице падал, и его повторяли после ещё одного `wait`.
- **Устаревшие ref.** «Element has been garbage collected», «No element found with reference» после перерисовки мастера. Dropzone заменяет input после каждой загрузки, поэтому ~15 вызовов `find` ушло только на повторный поиск input.
- **Промахи `find`.** Не находит свёрнутое и то, что за пределами экрана. Один раз вернул кнопку меню вместо пункта меню. Длинные списки в меню агент докручивал через JS `scrollIntoView`, иначе `find` пункт не видел.
- **Сохранение не подтверждается.** «Первый клик не сработал, кликаю ещё раз». На самом деле сервер вернул HTTP 409, и это было видно только через `read_network_requests`. Агент 31 раз читал сетевой лог вокруг кнопок Save.
- **Загрузка файлов.** Лимит 10 МБ на загрузку, файлы приходилось копировать в scratchpad. Сервер принял скриншоты, но их обработка упала из-за альфа-канала. Узнать это удалось только запросом к внутреннему API.
- **Сбои транспорта (~13):**
  - «Detached while handling command» ×5;
  - таймаут `captureScreenshot` 30 с ×2;
  - таймаут `Runtime.evaluate` 45 с;
  - вкладка выпала из группы.
- **Диалог «Leave site?».** Агент ушёл со страницы через `force:true` и потерял правки.
- **Цензура вывода.** `[BLOCKED: JWT token]` на строке «1.0.0» и `location.pathname`. Агент обходил это через `.split('').join(' ')`.
- **Отказы классификатора разрешений (3).** Клик Save по координатам и DELETE через fetch пришлось делать пользователю вручную.

**Для чего агент 109 раз вызывал `javascript_tool`:**
- ~50% — прочитать текст области или диалога;
- ~12% — установить значение через нативный setter, в том числе textarea на ~1500 символов, select и группы чекбоксов;
- ~10% — получить список полей с подписями и значениями;
- ~8% — пройти мастер циклом «шаг → Далее → пауза»;
- ~8% — подождать условие;
- ~8% — проверить результат: disabled, текст ошибки, выбранная вкладка;
- ~8% — запросы к внутреннему API, чтобы узнать состояние, которого нет в интерфейсе.

**Время.** На фиксированные ожидания ушло ~820 с. Медиана `browser_batch` 5 с, и это в основном ожидания. Лишние циклы: `find` перед каждым кликом, батчи из одного действия.

**Требования к agent-click, которые следуют из этой сессии:**
1. После каждого действия ждать, пока страница успокоится, и возвращать состояние или дифф. Автоматически показывать текст появившихся диалогов и toast-уведомлений.
2. Адресовать элементы стабильным номером или текстом. После перерисовки находить элемент заново по роли, имени и контексту (механизм ещё нужно продумать).
3. Локальный список элементов вместо `find`: компактный, включает диалоги и меню, можно ограничить областью.
4. `fill({n: value})` для React и Angular: нативный setter или `insertText`; select, группы чекбоксов, radio. В ответе возвращать, какое значение реально установилось.
5. Инструменты чтения: видимый текст основной области или верхнего диалога; список полей с подписью, значением и состоянием.
6. `upload(n, paths)` через `DOM.setFileInputFiles`, с поиском скрытого input за dropzone.
7. Показывать HTTP-статусы изменяющих запросов (POST/PATCH/DELETE), которые вызвало действие.
8. Надёжный транспорт: переподключение после detach, повтор при таймаутах, явный выбор при beforeunload.
9. Батч с условиями (`wait_for(text)`, «повторять до…») для мастеров (это ещё гипотеза).
10. Оставить `eval` как запасной выход для редких случаев.
11. Не портить обычные значения при скрытии секретов.
12. Описывать действия семантически («нажать "Сохранить" в диалоге X»), чтобы классификатор разрешений легче их пропускал (гипотеза).

### 32ce617b: flowr, пункт 57 чеклиста (цены и пробные периоды подписок)

**Задача.** Проверка ключа APNs в Firebase, продуктов в RevenueCat, вступительных предложений в App Store Connect (ASC) и Play Console. Затем запись: цены в обоих магазинах (базовая цена в долларах с пересчётом по странам плюс ручная цена для Польши), пробный период `free-trial-3d` на два базовых плана в Play, названия группы подписок в ASC на трёх языках. Работа шла в четырёх тяжёлых SPA-консолях, двух вкладках и двух Google-аккаунтах.

**Как работал агент.** Батч почти всегда устроен как «действие → фиксированная пауза → наблюдение»: в 133 из 134 батчей был `wait`. Последним действием батча был скриншот (65 раз) или `find` (50). Элементы агент находил то кликом по координатам (~57), то по ref (~49). Все ref он получал через `find` (78 использований), а `read_page` вызвал всего один раз. `find` часто служил просто для чтения значений: «значение поля Offer ID», «цена в строке Польши», «сообщение "изменения сохранены"».

**Трения:**
- **Страница не готова после navigate (~10 раз).** `get_page_text` возвращал «No text content found», `find` не находил элемент. После дополнительного `wait 3` повтор срабатывал.
- **Сбои скриншотов (7 раз, ~165 с).** Пять таймаутов `captureScreenshot` по 32–33 с, в том числе на активной вкладке. Два «Detached while handling command». На RevenueCat скриншоты были запрещены на уровне домена.
- **Слепые цепочки кликов по координатам.** Батч «добавить фазу → открыть тип → Free trial → длительность → единица» переиспользовал координаты из предыдущего прогона и ушёл мимо цели: «диалог не открылся», «Dropdown didn't register», «всё ещё Months». Шаги внутри батча никто не проверял. Итог: ~6 лишних циклов и ~70 с.
- **Клик по ref не сработал**, а клик по координатам в ту же точку сработал.
- **Кастомные dropdown (~8 выборов, по 2–3 цикла каждый).** Открыть → `wait 1` → `find` нужного пункта → `scroll_to` → клик. За один шаг выбор получился только в нативном `<select>`.
- **Замена значения поля.** Девять раз triple_click + type: отдельного действия «установить значение» нет.
- **Вкладки.** Новая вкладка открылась со скриншотом 758x43. `tabs_close` упал. Неверный индекс аккаунта (`/u/N`) перенаправил на страницу регистрации.
- **Шум в `get_page_text` на Play.** В тексте оказались лигатуры иконок (`arrow_right…expand_more`), а основного содержимого не было.
- **Маленький viewport (1280x543)** заставлял часто прокручивать: 6 scroll и 22 scroll_to.
- **Нестабильные ref.** Ref постоянно росли (до ref_7685), один и тот же чекбокс перенумеровывался после каждой перерисовки.

**Время.** Инструменты работали ~1720 с: ~384 с фиксированных пауз (22%), ~165 с таймаутов скриншотов (10%). Модель думала ~21 мин суммарно, в среднем 5,7 с между вызовами. Лишние циклы: `find` перед каждым кликом, скриншот после каждого действия (действие само состояние не возвращает), повторы после слишком коротких пауз.

**Требования к agent-click, которые следуют из этой сессии** (в дополнение к 3bbafecf):
1. `navigate` ждёт реального содержимого: основная область страницы не пустая. Явно сообщает о редиректах на логин, регистрацию или /home.
2. В списке элементов у каждого есть текущее значение и состояние: value, checked, selected, expanded, href, а также в каком диалоге или секции он находится и к какой строке таблицы относится. Тогда `find` для чтения значений не нужен.
3. `fill`, `select`, `check` — каждое одним действием. `select` работает и для нативного select, и для кастомных listbox: открыть → выбрать по тексту → проверить. Для длинных списков возможна фильтрация вводом (гипотеза).
4. Батч проверяет каждый шаг и останавливается на неожиданном состоянии: ожидаемый диалог не открылся, цель пропала или чем-то перекрыта.
5. Можно выбрать цель по тексту и области: «нажать "Set prices" в секции "Price and availability"». Без отдельного вызова модели.
6. Скриншот с жёстким таймаутом около 3 с. Если не успел, отдаём текстовое состояние. Для фоновых вкладок включаем эмуляцию фокуса.
7. Новые вкладки и popup-окна видны в результате действия, к ним можно переключиться, у них нормальный viewport.
8. Фиксированный и достаточно большой viewport, его размер указан в выводе.
9. Чтение основного текста страницы без навигации и лигатур иконок.
10. Чтение таблиц с учётом структуры: строки × столбцы, чекбоксы и действия привязаны к подписи строки, поиск внутри таблицы (гипотеза).
11. Подтверждение рискованных действий (сохранение, цены): помечать их, но не блокировать (гипотеза).

### 73e3054b: rostemo, реклама в Meta Ads и настройка GTM/Stape

**Задача.**
- **A. Ads Manager.** Кампания «Трафик»: название, группа объявлений, цель, бюджет, дата окончания (выбор даты), локация (подсказки при вводе) и радиус, возраст, интересы, площадки. Пользователь прервал: «Ты создавал рекламу не на том аккаунте». Агент взял единственный рекламный аккаунт, который видел.
- **B. Business Suite.** Выдать доступ к странице.
- **C. Креатив и публикация.** Креатив (видео, текст), публикация. После публикации статус оставался «Черновик», пока страницу не перезагрузили.
- **D. Web-GTM и server-side GTM на Stape.** Переменные, триггеры, теги. Пользователь остановил: «Чем именно ты занимаешься? В прошлый раз настройка sGTM на stape не была такой сложной».

**Как работал агент.**
- Основной шаблон батча — «действие → wait N → скриншот»: 125 батчей из трёх действий, 133 заканчивались скриншотом.
- **Целился в основном по координатам:** 221 действие по координатам против 47 по ref. Ref почти всегда получал через `find` (45 вызовов), то есть платил лишним циклом «find → клик».
- **Состояние читал:**
  - скриншотами, в GTM уменьшенными до 0,5–0,6 (по просьбе пользователя);
  - `zoom`, чтобы проверить чекбоксы;
  - выгрузкой всего текста страницы через `get_page_text`;
  - вопросами к `find` вида «…with checked state».

**Трения:**
- **Клик без эффекта и повтор (~7).**
  - Чекбокс не снялся кликом по координатам, сработал клик по ref.
  - Клик по ref «Назначить пользователей» ничего не открыл, сработал клик по координатам.
  - Выбор типа в GTM не открылся, а `find` вернул ячейку таблицы со страницы под диалогом.
- **Ввод текста (~4).**
  - В поиск интересов попала лишняя буква.
  - Код в редакторе GTM не зарегистрировался («Необходимо указать значение»).
  - 19 раз triple_click/ctrl+a для очистки полей.
  - ~8 кликов в пустое место, чтобы снять фокус и зафиксировать значение.
- **Кастомные dropdown и поля с подсказками (~8 виджетов, по 2–3 вызова на каждый).**
  - Цель кампании выбралась не та.
  - В списке возраста `find` не видел текста пунктов, пришлось листать список и смотреть через `zoom`.
  - Радиус, локация, интересы, выбор страницы — по 2–3 вызова каждый.
  - Нативный `<select>` через `form_input` срабатывал с первого раза (4 из 4).
- **`find` ошибался или не находил (6).**
  - Не находил элементы за пределами экрана и свёрнутые.
  - Сказал, что все площадки отмечены, сразу после того как агент снял с них отметку.
  - Путал элементы.
- **Побочные эффекты клавиш.** Escape открыл диалог «Опубликовать черновики?» и закрыл редактор. Пришлось перейти на страницу заново, это 13,9 с.
- **Инфраструктура.**
  - Расширение отключилось посреди батча, а позже пропало совсем.
  - Таймаут `captureScreenshot` ~40 с ×3 на страницах GTM.
  - `file_upload` отказал на видео из-за лимита 10 МБ, загружать пришлось пользователю (166 с).
- **Навигация.** URL Business Suite перенаправил в другой бизнес-аккаунт.

**Время.**
- Инструменты работали ~1675 с, из них **552 с (33%) — фиксированные паузы**. После каждой навигации агент ждал 6–8 с.
- Модель думала ~23 мин суммарно (~278 пауз по 5 с).
- `scroll` возвращал свою картинку вдобавок к явному скриншоту (`[img x2]` 28 раз), токены на изображения удваивались.
- В GTM одна и та же цепочка координат повторялась шесть раз, чтобы создать шесть переменных, по 2–3 вызова на переменную.

**Требования к agent-click, которые следуют из этой сессии** (в дополнение к предыдущим):
1. Номера на скриншоте и в списке элементов приходят в одном ответе, без отдельной модели для поиска.
2. У элементов в списке есть состояние: checked, выбранное значение, expanded, disabled, пункты listbox, секция или диалог.
3. Цель можно указать по тексту, даже если она за пределами экрана: инструмент сам докрутит и выполнит действие.
4. Проверка клика: не перекрыт ли элемент (`elementFromPoint`) и что изменилось — «видимых изменений нет», «открылся диалог X», «открылась вкладка Y».
5. `fill` очищает поле, устанавливает значение и фиксирует его (blur). Работает с contenteditable. Поддержка редакторов кода (CodeMirror/Monaco) — гипотеза, её нужно проверить.
6. `select` для полей с подсказками: ввести запрос, дождаться подсказок, выбрать по тексту.
7. Прокрутка внутри контейнера по номеру элемента, одна картинка на ответ.
8. Батч по тексту и подписям, а не по координатам, чтобы однотипные формы проходились одним вызовом.
9. Переподключение CDP, сохранение номеров элементов после кратковременных обрывов.
10. Запасной выход для чтения состояния страницы (JS evaluate) оставить: он понадобился для диагностики пикселя и GTM.
11. Показывать контекст страницы: выбранный аккаунт или рабочее пространство из шапки. Это спасло бы от работы «не на том аккаунте». Подтверждение перед публикацией — гипотеза: неясно, что должен делать инструмент, а что агент.

Форм в этих сессиях не заполняли: только навигация, просмотр и одна диагностика через JS.

**Трения:**
- **Зависающие скриншоты — главная причина медленных `computer`.** В 6c095b77 4 из 7 скриншотов упали по таймауту 30 с («renderer may be frozen»). В 6a0b7282 окно было свёрнуто (`innerWidth 0`, `visibility:hidden`), `resize_window` не сработал, и пользователю пришлось развернуть окно вручную. В скрытой вкладке фиксированные паузы растягивались: `wait 8` занял 15 с.
- **`navigate` не дожидается загрузки.** Пустой `get_page_text`, текст «Loading team info…». Агент ставил паузы 3–5 с, а один раз ждал окончания обработки сборки шестью `wait 10` подряд (70 с).
- **Промах по координатам.** Открылась карточка не того пользователя.
- **Устаревший ref после смены URL** обрывал весь батч: «0 completed, 2 remaining».
- **Тихие редиректы.** Агент заметил их только по URL в подвале ответа.
- **Шум лигатур иконок в тексте Play Console.**
- **Диалоги** закрывались кликом по координатам или Escape.
- **Инфраструктура.** «Browser disconnected» ×3. Запрет чтения страниц на домене. В каждой сессии приходилось заново создавать группу вкладок (`createIfEmpty`).
- **Отладка своего сайта (AdSense)** — особый класс задач: JS (`data-ad-status`, consent, `performance`) и сетевые запросы. Сетевой лог в Claude in Chrome начинает писать только с первого вызова, поэтому страницу приходилось перезагружать.

## Сводные выводы по всем сессиям

**Что повторяется везде:**
1. **Фиксированные паузы — 22–35% времени инструментов.** Причина в том, что действия не ждут стабилизации страницы и не возвращают состояние. Отсюда шаблон «действие → wait → скриншот» в каждом батче.
2. **`find` используется как костыль:** отдельный вызов модели ради ref, ~2–3 с на каждый. Его же агент использует, чтобы читать значения и состояния. Ошибается на элементах за пределами экрана, свёрнутых и в диалогах.
3. **Клики по координатам:** промахи, слепые цепочки, повторы. Клики по ref иногда тоже не срабатывают молча. Ни один клик не проверяется.
4. **Ввод.** Нет действия «установить значение»: очистка через triple_click/ctrl+a и клик в пустое место. Агент сам писал хелперы с нативным setter. Кастомные dropdown и поля с подсказками занимают 2–3 цикла каждый, нативный `<select>` работает с первого раза.
5. **Ref нестабильны после перерисовки** (React, мастера, dropzone).
6. **Таймауты скриншотов по 30–40 с** на фоновых, свёрнутых и тяжёлых вкладках. Сюда же отключения транспорта.
7. **Результат не видно.** Ошибки сохранения (HTTP 409), редиректы, статусы, которые обновляются только после перезагрузки страницы.
8. **Загрузка файлов:** лимит 10 МБ, файлы приходится копировать, input за dropzone трудно найти.
9. **JS как запасной выход** нужен: для чтения текста и состояния (это закроют нормальные инструменты) и для диагностики (это не закроют).
10. **Контекст аккаунта** (рекламный аккаунт, `/u/N`, бизнес-аккаунт): работа «не в том аккаунте» уже случалась.

## Самоотчёты сессий (2026-10-26)

Две сессии flowr сами описали свой опыт по ретроспективному промпту. Полные тексты: [self-reports/flowr-store-release.md](self-reports/flowr-store-release.md) (3bbafecf) и [self-reports/flowr-store-billing-setup.md](self-reports/flowr-store-billing-setup.md) (32ce617b). Обе сессии прошли через compact, поэтому первую половину помнят только по резюме.

**Новое по сравнению с разбором логов:**
1. **Интерфейс расходится с реальным состоянием на сервере.** Это самый важный пункт.
   - ASC показывал «8 из 10 скриншотов», хотя все они были в `FAILED`. Подписки в UI значились «Готово», а в API — `MISSING_METADATA`.
   - Правду показал только read-only GET к внутреннему API. Ни скриншот, ни дерево элементов её не отражают.
   - Сессия предлагает отдельный инструмент `read_api` только для GET. Так harness сможет разрешать чтение без вопросов, а запись — нет.
2. **Сеть — самый надёжный способ проверить результат.** Сессии нужны статусы изменяющих запросов вместе с текстом ошибки (пример: 409 «name already used»). Без этого ошибки молчаливые. Заметки для ревью «сохранились» только в резюме, а на сервере их не было.
3. **«Загружается» не отличить от «пусто».** Firebase на недогруженной странице показывал «Disabled». Нужен явный флаг `settled` и признаки загрузки: спиннеры, скелетоны, `busy`.
4. **Слои.** Когда открыт modal, нужно видеть только его элементы. Элементы под ним `find` подмешивал. Нужен признак перекрытия, например «кнопка под липким футером».
5. **Неоднозначные подписи полей.** Четыре поля «Контактная информация». Различить их удалось только по `id` и `placeholder` (`contactPhone`).
6. **Неактивные вкладки (tabpanel).** `find` не видел input в неактивной вкладке и сообщал, что элемента нет.
7. **Запрошенное против фактического.** Ввели 199.99, консоль показала 244.99 (добавила НДС). «Days» не переключилось, а клик считался успешным. `fill` и `select` должны сравнивать запрошенное значение с итоговым.
8. **Тихий успех — самое вредное.** Клик «успешен», модалка не открылась, а батч продолжил и ввёл «3» в неизвестное место. Около половины вызовов уходило на проверки.
9. **Подтверждение модалки только при совпадении текста** («язык: польский»), чтобы не подтвердить удаление не того объекта.
10. **Батч бесполезен, если каждый шаг требует свежий ref.** Harness просил использовать batch, но шаги зависели друг от друга. Указание цели по тексту делает батч осмысленным.
11. **Масштаб скриншота.** При `scale: 0.6` агент пересчитывал координаты в уме — постоянная нагрузка и источник промахов. Решается метками вместо координат.
12. **Мусор в выводе.** `read_page` на select из 50 локалей выдал 50 option и 50 дублей. Список нужно сворачивать: «50 options, selected: pl».
13. **`find` всё-таки ценят** за одно: на запрос из нескольких целей он сразу возвращал несколько ref. Подписи `find` — пересказ модели, ему не доверяли.

**Уточнение к разбору rostemo.** Скриншоты уменьшались до 0,5–0,6 по просьбе пользователя, а не по решению агента.
