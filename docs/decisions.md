# Журнал решений

Формат: дата, решение, почему, отвергнутые альтернативы. Замещённые решения не удаляем, а помечаем `ЗАМЕЩЕНО → D-N`.

## D-1. Подключение к браузеру через CDP autoConnect, без расширения (2026-10-26)

**Решение.** Подключаемся к уже запущенному Brave пользователя по CDP. Удалённая отладка включается один раз переключателем `brave://inspect/#remote-debugging` («Allow remote debugging for this browser instance»). При каждом подключении браузер спрашивает Allow. Адрес и порт берём из файла `User Data\DevToolsActivePort`.

**Почему.**
- Работает в основном профиле: куки, сессии, всё видно пользователю.
- Доверенный ввод (`Input.dispatchMouseEvent`, `isTrusted=true`) доступен из коробки.
- Весь код в одном процессе.

**Отвергнуто.**
- Флаг `--remote-debugging-port`: в Chromium 136+ не работает с основным профилем.
- Своё MV3-расширение и WebSocket-мост: для доверенного ввода всё равно нужен `chrome.debugger` с той же плашкой «браузер отлаживается», а кода примерно вдвое больше.
- Headless или отдельный профиль: нет кук пользователя, действия не видны.

**Последствия.** Allow подтверждается на каждое подключение. Пока работаем одним процессом, это происходит раз за сессию Claude Code. Если станет мешать, можно перейти на демон (см. открытые вопросы в architecture.md).

**Статус окружения (2026-10-26).** Brave 1.98.60 / Chromium 156: функция поддерживается (появилась в Chromium 144). Переключатель у пользователя пока не включён: нет `DevToolsActivePort`, нет ключа `remote_debugging` в `Local State`.

## D-2. Язык: TypeScript, не Rust (2026-10-26)

**Решение.** Сервер пишем на TypeScript (Node 22). Библиотеки: `@modelcontextprotocol/sdk`, `puppeteer-core` (CDP), `sharp` (метки и JPEG).

**Почему.** Время шага агента определяют модель (3–15 с) и загрузка страницы (0,3–3 с). Скриншот кодирует сам браузер. Сбор элементов в любом случае выполняется как JS внутри страницы. Rust сэкономил бы около 10 мс на обработке картинки, это меньше 1% шага. В TS эталонный MCP SDK и зрелая CDP-библиотека.

**Отвергнуто.** Rust (`rmcp`, `chromiumoxide`): выигрыша на горячем пути нет, CDP-экосистема слабее, итерации медленнее. Единственный плюс, один бинарник, для личного инструмента неважен.

**Уточнение (2026-10-26).** Логи прошлых сессий показали, что в Claude in Chrome инструмент выполнялся 5–10 с на batch, дольше паузы модели (3–4 с). Источник задержек — паузы и ожидания внутри инструмента, а не язык. Решение остаётся в силе (см. research/usage-history.md).

**Принцип скорости.** Скорость получаем архитектурно: меньше циклов «вызов → ответ», меньше токенов, никаких фиксированных пауз.

## D-3. Метки рисуются на скриншоте на стороне сервера (2026-10-26)

**Решение.** Скриншот снимается чистым, номерные метки накладываются в сервере (`sharp`), а не через оверлеи в DOM.

**Почему.** Пользователь не видит мерцания, страница и вёрстка не меняются.

## D-5. Действия выполняются одним инструментом `act` со списком шагов (2026-10-26)

**Решение.** Все действия (click, fill, select, check, press, scroll, upload, wait_for, expect) — это шаги одного инструмента `act(steps)`. Один шаг — частный случай.

**Почему.** Батч — естественный режим работы, агенты и так им пользовались. Отдельные инструменты возвращают лишний цикл «вызов → ответ» на каждый шаг. Батч осмыслен потому, что цель можно указать текстом и каждый шаг проверяется. Самоотчёт 3bbafecf: батчить было нечего, пока каждый шаг требовал свежий ref.

**Отвергнуто.** Отдельные `click`/`fill`/`select` + `batch`.

## D-6. Скриншоты: режим auto, но агент может потребовать картинку (2026-10-26)

**Решение.** По умолчанию картинка прикладывается, только когда экран заметно изменился. Агент в любой момент может явно её запросить: `look({image: "always"})` или опция `screenshot: true` у `act`/`navigate`.

**Почему.** Список элементов несёт основной смысл, а картинки дорогие. Но инструмент может ошибиться в оценке «значительного изменения», и агент не должен из-за этого остаться без картинки.

## D-7. Подтверждение рискованных действий — не задача инструмента (2026-10-26)

**Решение.** Инструмент не подтверждает и не блокирует публикацию, оплату и удаление.

**Почему.** Harness Claude Code (классификатор разрешений) уже блокирует такие действия. Логи это подтверждают: отказы на Save и DELETE. Задача инструмента — описывать действия семантически («click "Сохранить" in dialog X»), чтобы классификатору было что оценивать. Защиту от подтверждения не того объекта даёт шаг `expect` (проверка текста диалога перед кликом), а не отдельный механизм.

## D-8. `eval` остаётся как последнее средство (2026-10-26)

**Решение.** Инструмент `eval(js)` есть. В его описании для агента прямо сказано: использовать, только если ни один другой инструмент не подходит (диагностика пикселей, consent и т.п.).

**Почему.** Почти всё, ради чего агенты писали JS (109 вызовов в 3bbafecf), закрывают `read`, `fill`, `wait_for`, `read_api` и сетевые запросы в ответе `act`. Без запасного выхода агент застрянет на редких задачах. Записи через `eval` по-прежнему контролирует harness.

## D-9. Сбор элементов (2026-10-26)

Подвопросы перечислены в architecture.md, пункт 2.

- **а) Источник.** Свой JS в странице плюс библиотека `dom-accessibility-api` для имён и ролей по спецификации accname. Отвергнуто: CDP Accessibility (нет геометрии и видимости, тяжело на больших SPA) и CDP DOMSnapshot (нет имён и ролей).
- **б) Интерактивность.** Стандартные теги, роли, tabindex, contenteditable плюс эвристика `cursor:pointer` для div с обработчиками. Вложенные дубли отсекаются: если внутри кликабельного блока есть кнопка, показываем только кнопку.
- **в) Текст.** Интерактивные элементы плюс короткий значимый текст: заголовки, статусы и бейджи, пары «подпись — значение», ячейки строки рядом с её действиями. Длинный текст сворачивается. Почему: агентам постоянно нужны статусы и значения («Черновик», «FAILED», «PLN 244.99»).
- **г) Контекст.** Путь из диалога, landmark-области, заголовка, fieldset или группы и строки таблицы, не глубже трёх уровней. Элементы группируются под общим заголовком контекста, путь у каждого не повторяется.
- **д) Видимость и слои.** Модальный слой по `aria-modal`, `<dialog>` и `inert`. Перекрытие через `elementFromPoint` в нескольких точках. *Нужно проверить на практике.*
- **е) Номера.** Подход Claude in Chrome (WeakRef-карта) плюс отпечаток элемента для повторного поиска после перерисовки. Освободившиеся номера не используются повторно. Подробности ниже.
- **ж) Фреймы.** В MVP: shadow DOM и iframe того же origin. Cross-origin iframe (OOPIF) через отдельное подключение CDP — второй этап.
- **з) Дифф.** Снимки до и после действия сравниваются по номерам. Автоскриншот, если сменился слой или URL либо изменилась заметная доля видимых элементов. *Порог подбирать на практике.*
- **и) Производительность.** Цель — меньше 50 мс на сбор на тяжёлом SPA. Лимит размера вывода, элементы за экраном — сводкой по секциям.

**Подробности по (е).** WeakRef из Claude in Chrome хранит ссылку на конкретный DOM-узел. Он переживает перерисовку, только если фреймворк обновил существующий узел. Если узел пересоздан (смена `key`, условный рендер, dropzone, шаг мастера), ссылка умирает. Логи это подтверждают: «Element has been garbage collected», «ref_stale», один и тот же чекбокс получил номера ref_3382 → ref_4624. Поэтому к WeakRef добавляется отпечаток: роль, имя, путь контекста и порядковый номер среди одинаковых в этом контексте. Если узел умер, элемент ищется заново по отпечатку и получает тот же номер. Если кандидатов несколько или ни одного, инструмент ничего не угадывает и возвращает ошибку с актуальным состоянием.

## D-4. Процесс: один MCP-процесс по stdio для MVP (2026-10-26)

**Решение.** Claude Code запускает сервер по stdio, и сервер сам держит CDP-подключение. Демон с тонким MCP-клиентом откладываем, пока не появится реальная потребность.
